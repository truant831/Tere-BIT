# CyberSafe RP2040 — отчёт по исследованию

Исследование выполнялось в учебных целях на собственном оборудовании и собственных копиях прошивки.

CyberSafe использует RP2040. Пользователь выбирает цифру вращением энкодера и подтверждает её нажатием на ручку энкодера. После четырёх цифр прошивка проверяет PIN и при успехе открывает USB Mass Storage.

## Краткие параметры

| Параметр | Значение |
|---|---|
| MCU | RP2040 / Cortex-M0+ |
| Прошивка | `usb_token v0.1` |
| Flash | 2 MiB |
| Код | `0x10000000–0x100067EF` |
| Виртуальный диск | `0x10100000`, размер 1 MiB |
| Файловая система после восстановления | FAT12 |

## Найденные векторы

1. Перебор PIN через эмуляцию энкодера.
2. Получение PIN статическим анализом прошивки.
3. Извлечение файловой системы из полного Flash-дампа без PIN.
4. Полный дамп Flash через SWD.
5. Чтение через SWD только области виртуальной файловой системы.
6. Обход PIN через hardware breakpoint и подмену регистра.
7. Поиск логики через hardware watchpoint.

## Общий этап: обработка `your_prize.zip`

После любого вектора, который давал доступ к виртуальному диску, в корне находился:

```text
your_prize.zip
```

Размер: `691868` байт.

Внутри:

```text
layers.zip
readme.txt
```

`readme.txt` сообщал, что внутри 1337 ZIP-слоёв. Пароль каждого слоя равен его номеру:

```text
layer_1.zip    -> 1
layer_2.zip    -> 2
...
layer_1337.zip -> 1337
```

Распаковку автоматизировали. В приложенных материалах есть воспроизводимый скрипт:

```bash
python tools/unpack_layers.py layers.zip
```

После 1337-го слоя получается `prize.html`. В нём находится:

```html
<title>Rickrolled!</title>
<h1>Ты открыл 1337 слоёв!</h1>
```

и встроенный GIF с Rick Astley.

## 1. Перебор PIN через другой микроконтроллер

Я подключил Raspberry Pi Pico к линиям энкодера и начал программно эмулировать его вращение и нажатие.

Видео с объяснением:

[encoder_emulation_explanation.mp4](media/bruteforce/encoder_emulation_explanation.mp4)

Таймлапс пайки:

[contact_soldering_timelapse.mp4](media/bruteforce/contact_soldering_timelapse.mp4)

Ключевая функция:

```python
def number(num):
    delay = 27500

    if num <= 5:
        for i in range(0, num):
            second_pin.off()
            sleep_us(delay)
            fisrt_pin.off()
            second_pin.on()
            sleep_us(delay)
            fisrt_pin.on()
            second_pin.on()
            sleep_us(delay)
    else:
        for i in range(0, 10 - num):
            fisrt_pin.off()
            sleep_us(delay)
            second_pin.off()
            fisrt_pin.on()
            sleep_us(delay)
            fisrt_pin.on()
            second_pin.on()
            sleep_us(delay)

    btn.off()
    sleep_us(delay)
    btn.on()
    sleep_us(delay * 50)
```

Полный код: [`code/hack.py`](code/hack.py).

Комбинации перебираются от `0000` до `9999`.

После неправильной комбинации устройство примерно на 3 секунды блокирует ввод. Только эта задержка даёт:

```text
3 с * 10000 = 30000 с = 8 ч 20 мин
```

Реальное время больше из-за самого ввода четырёх цифр.

Таймлапс:

[password_bruteforce_timelapse.mp4](media/bruteforce/password_bruteforce_timelapse.mp4)

После успешного подбора появляется USB-диск. Затем используется [общий этап ZIP](#zip-stage).

**Класс:** brute force / аппаратно-программный.  
**Сложность:** низкая–средняя.  
**Статус:** подтверждено.

## 2. Статический анализ прошивки

`backup_prog.bin` имеет размер `0x67F0 = 26608` байт и загружается в IDA как ARM little-endian по адресу `0x10000000`.

В IDA была найдена функция:

```text
password_input_loop = 0x10000ABA
```

Фото графа:

![password_input_loop](assets/ida/password_input_loop_graph.jpg)

В псевдокоде проверки было:

```c
entered_code[v10 - 1] == *(_BYTE *)(v10 + 268457215)
```

Константа:

```text
268457215 = 0x100054FF
```

Для `v10 = 1..4` получаются адреса:

```text
0x10005500
0x10005501
0x10005502
0x10005503
```

В этих четырёх байтах:

```text
02 01 03 09
```

Фото:

![PIN в Flash](assets/ida/password_hex_0x10005500.jpg)

Следовательно:

```text
PIN = 2139
```

Адрес PIN был найден не поиском случайной последовательности, а через операнд в цикле сравнения введённого PIN с эталонным.

Видео IDA:

[ida_analysis_timelapse.mp4](media/ida/ida_analysis_timelapse.mp4)

После ввода `2139` можно открыть диск и перейти к [общему этапу ZIP](#zip-stage).

**Класс:** reverse engineering / hardcoded secret.  
**Сложность:** средняя.  
**Статус:** подтверждено.

## 3. Извлечение файловой системы из Flash без PIN

В MSC callback была найдена область:

```text
XIP:       0x10100000
offset:    0x00100000
size:      0x00100000
sector:    512 bytes
sectors:   2048
```

Это 1 MiB backing storage виртуального диска.

Данные дополнительно проходят XOR-преобразование. Для восстановления используется:

```bash
python tools/decrypt_rp2040_disk.py backup.bin decrypted_flash_disk.img
```

После декодирования получается FAT12-образ и из него извлекается `your_prize.zip`.

Далее: [общий этап ZIP](#zip-stage).

**Класс:** reverse engineering / data-at-rest.  
**Сложность:** средняя.  
**Статус:** подтверждено.

## 4. Полный Flash-дамп через SWD

На готовом устройстве удобного SWD-разъёма нет. Для прямого подключения используются выводы RP2040:

```text
pin 24 = SWCLK
pin 25 = SWDIO
```

и общая земля.

Чтобы не паять выданную плату CyberSafe, возможность подпайки к QFN-56 сначала проверялась на отдельной RP2040-Zero с тем же RP2040.

Фото:

![Подпайка SWD](assets/swd/rp2040_swd_solder_closeup.jpg)

![Масштаб пайки](assets/swd/rp2040_swd_solder_scale.jpg)

Через OpenOCD:

```text
cortex_m smp off
targets rp2040.core0
halt
```

Сначала было прочитано 4096 байт, затем 26608 байт программы. `swd_dump.bin` совпал с `backup_prog.bin` по SHA-256:

```text
1713db3fe890afe02303fd5bafc6d7d1a389b6d0c5786262119bb4d5a11815e4
```

Полный дамп:

```powershell
dump_image rp2040_xip_full.bin 0x10000000 0x200000
```

Размер:

```text
2097152 bytes
```

**Класс:** аппаратная / SWD.  
**Сложность:** средняя из-за пайки.  
**Статус:** подтверждено.

## 5. Чтение только файловой системы через SWD

Полный дамп не обязателен.

Область виртуального диска:

```text
0x10100000
```

Размер:

```text
0x100000
```

Поэтому можно читать только её:

```powershell
dump_image vfs_raw.bin 0x10100000 0x100000
```

Дальше `vfs_raw.bin` декодируется тем же алгоритмом, что и в векторе №3.

Этот способ отличается от полного дампа тем, что код прошивки вообще не копируется.

**Класс:** targeted memory read / SWD.  
**Сложность:** низкая после нахождения адреса.  
**Статус:** адрес и чтение XIP подтверждены; нужен отдельный лог именно этой команды.

## 6. Обход PIN через hardware breakpoint

IDA дала область `password_input_loop`, но конкретное место проверки дополнительно искалось и подтверждалось динамически через SWD.

Сначала breakpoint ставился на:

```text
0x10000C5A
```

После подтверждения цифры нажатием на ручку энкодера процессор останавливался в пути обработки ввода.

Затем breakpoint перенесли на:

```text
0x10000C86
```

Пошаговое выполнение показало последовательность:

```asm
0x10000C86: LDRB R2, [R3, R4]
0x10000C88: LDRB R3, [R5, R4]
0x10000C8A: CMP  R2, R3
```

Наблюдение регистров показало:

```text
R2 = введённая цифра
R3 = ожидаемая цифра PIN
R4 = позиция проверяемой цифры
```

После этого breakpoint ставился уже непосредственно перед сравнением:

```text
bp 0x10000C8A 2 hw
resume
```

Перед `CMP` значение `R2` заменялось значением `R3`:

```text
reg r2 <значение R3>
step
resume
```

Подмена повторялась четыре раза. После четвёртого сравнения USB-диск открылся.

Фото:

![SWD](assets/swd/swd_terminal_and_usb_drive.jpg)

Важный момент: hardware breakpoint теряется после полного снятия питания. В одном из повторов плата была обесточена, breakpoint не поставили заново, и из-за этого казалось, что метод перестал работать.

**Класс:** runtime manipulation через SWD.  
**Сложность:** средняя.  
**Статус:** подтверждено.

## 7. Hardware watchpoint

Breakpoint останавливает процессор на известной инструкции.

Watchpoint останавливает процессор, когда меняется интересующий адрес RAM.

Если уже известен:

```text
password_ok = 0x20002ED2
```

можно поставить:

```text
wp 0x20002ED2 1 w
resume
```

### Watchpoint без IDA

Можно обойтись вообще без предварительного анализа прошивки.

1. Снять RAM:
   ```text
   dump_image ram_before.bin 0x20000000 0x42000
   ```
2. Подтвердить одну цифру энкодером.
3. Снять RAM второй раз:
   ```text
   dump_image ram_after.bin 0x20000000 0x42000
   ```
4. Сравнить два файла и найти байты, которые меняются вместе с введённой цифрой.
5. Поставить:
   ```text
   wp <candidate_address> 1 w
   resume
   ```
6. При следующей записи CPU остановится на инструкции, которая пишет цифру.
7. Посмотреть:
   ```text
   debug_reason
   reg pc
   reg
   ```

Так можно динамически найти функцию ввода, не зная заранее `password_input_loop` и `0x10000C8A`.

**Статус:** метод подготовлен, но отдельный WP-эксперимент ещё нужно повторить и зафиксировать.
